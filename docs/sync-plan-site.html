Garage Sync Plan
Roles Server Testing Laptops Conflicts
Server first -> Test -> Link laptops

Offline-first sync checklist for the Garage app

Goal: Multiple laptops work offline with SQLite, then sync online through an HTTPS API, with real conflicts and a conflict UI that the team can resolve quickly.

Start with server Jump to tests
Flow Server foundation -> HTTPS API -> Hardening -> Testing -> Laptops -> Conflict UI

Phase 0 - Roles and access

No SSH sharing. HTTPS only for laptops.

Owner (server admin)

Friend

  • Keeps SSH and sudo access
  • Deploys and maintains the server
You + laptops

Client side only

  • Use HTTPS API only
  • No SSH required on laptops
Deliverables

What you receive

  • `API_BASE_URL` (example: https://sync.domain.com)
  • Way to create device tokens
  • Test device token for first laptop

Phase 1 - Server foundation

Friend does this first. Keep the project isolated and conflict-ready.

1.1

Isolate the project

  • Create a dedicated folder and service name for "garage-sync"
  • Do not touch existing hosted websites
1.2

Postgres (private)

  • Postgres is localhost-only (not public)
  • Dedicated DB and user for sync
1.3

Data model for conflicts

  • `records` table with versioning and soft delete
  • `sync_ops` table for idempotency
  • `devices` table for multi-laptop tokens
  • Every update increments `version`

Phase 2 - HTTPS sync API

All laptops sync through HTTP only. Conflicts are first-class.

2.1

Auth model

  • 1 master token (friend keeps it)
  • Unique `deviceToken` per laptop
  • Allow per-device revoke
2.2

Required endpoints

  • `POST /admin/devices` creates tokens
  • `POST /admin/devices/revoke` revokes tokens
  • `POST /sync/push` applies ops or returns conflicts
  • `GET /sync/pull?since=timestamp` returns updated records
2.3

Conflict response

Every conflict response must include both versions and the base version.

  • `tableName` and `recordId`
  • Server record: data, version, updatedBy/At
  • Client payload and `baseVersion`

Phase 3 - Deployment hardening

Keep it stable, secure, and backed up.

Runtime

  • Restart-on-crash service or Docker
  • Nginx with HTTPS (Lets Encrypt)

Firewall

  • Allow 22 (SSH), 80/443
  • Block everything else

Backups

  • Daily `pg_dump`
  • Keep 7-14 days

Phase 4 - Server testing

Do this before linking any laptops.

4.1

Health

  • `/health` returns OK
4.2

Device registration

  • Create device token via `/admin/devices`
  • Verify token works and can be revoked
4.3

Sync test

  • Push one record update
  • Pull it back
  • Version increments on server
4.4

Conflict test (critical)

  • Device A edits record at baseVersion 5
  • Device B pushes first (server -> version 6)
  • Device A pushes baseVersion 5 -> returns CONFLICT

Phase 5 - Laptop integration

Local SQLite + a reliable sync loop.

5.1

Local storage

  • Store `deviceId`, `deviceToken`, `lastSyncTime`
5.2

Local record metadata

  • `server_version`
  • `server_updated_at`
  • `server_updated_by`
  • `deleted_at`
5.3

Local ops queue

  • Write to local DB on edit
  • Append to pending ops
  • `baseVersion = local server_version`
5.4

Sync loop

  • Push pending ops
  • Store conflicts and do not overwrite
  • Pull updates since `lastSyncTime`
  • Apply updates and respect `deletedAt`
  • Update `lastSyncTime` with server time

Phase 6 - Conflict UI

Resolve conflicts without guessing.

6.1

Conflicts inbox

  • List open conflicts
  • Show tableName, recordId, created time
6.2

Resolver view

  • 3 panels: Mine, Theirs, Resolved
  • Buttons: Keep Mine, Keep Theirs, Merge, Save
6.3

Save resolution

  • Create new upsert op
  • `payload = resolved data`
  • `baseVersion = serverVersion` (latest)
  • Push, then mark conflict resolved locally
